# A 项目开发流程清单

本文档把 `作业要求.md` 与 `AI4SE_Final_Project_A_Coding_Agent_Harness.md` 合并成一条可执行路线，按完成顺序排列。项目选择为 **A · Coding Agent Harness**，语言暂定 **Python**，主要交互形态为 **CLI/TUI**，同时保留一个最小 WebUI 用于满足最终交付要求。

---

## 0. 先确定项目边界

在开始写 `SPEC.md` 前，先把项目边界定死，避免后面实现时范围膨胀。

你要做的是一个 **自己实现 harness 内核的 Coding Agent Harness**，不能只是配置现成 agent 框架。Superpowers / Codex / 其他编码智能体只能作为开发工具，不能成为最终产物自己的 agent loop。

本项目推荐定位：

> 一个面向小型代码仓库的终端式 Coding Agent Harness：它能组织上下文、调用 LLM 或 mock LLM、解析动作、执行受限工具、通过测试结果形成反馈，并用确定性护栏拦截危险动作。

必须提前确定的关键选择：

| 事项 | 建议选择 |
| --- | --- |
| 语言 | Python 3.11+ |
| 主交互 | CLI/TUI |
| 最小 WebUI | 浏览器中的演示控制台 / 日志查看器 |
| 重点机制 | 治理护栏 + 反馈闭环 |
| 测试方式 | pytest + mock/stub LLM |
| 分发方式 | Docker 优先，Python 包可选 |
| 凭据存储 | keyring 优先，`.env` 仅作为开发/容器 fallback 并说明风险 |

---

## 1. 安装并启用 Superpowers

这是通用要求中的强制项。正式进入规约前，需要选定一个支持 Superpowers 的编码智能体，并安装 Superpowers 插件或技能。

需要完成：

- 选择主开发智能体，例如 Codex CLI/App、Claude Code、Cursor Agent 等。
- 安装 Superpowers。
- 后续开发全过程如实遵循七步工作流。
- 若有任何偏离，在 `AGENT_LOG.md` 中记录原因。

Superpowers 七步流程必须覆盖：

1. `brainstorming`
2. `writing-plans`
3. `using-git-worktrees`
4. `subagent-driven-development` / `executing-plans`
5. `test-driven-development`
6. `requesting-code-review`
7. `finishing-a-development-branch`

---

## 2. Brainstorming：先做设计，不写实现代码

在 `SPEC.md` 和 `PLAN.md` 完成并通过冷启动验证之前，禁止写实现代码。

这一阶段要让 Superpowers 的 `brainstorming` 技能介入，反复追问项目到底解决什么问题、用户是谁、为什么值得做、harness 机制如何编码实现。

你需要在过程中主动质询 AI：

- 这个 harness 和普通脚本工具有什么区别？
- 哪些机制是代码实现，哪些只是提示词？
- 移除真实 LLM 后，核心行为还能不能用 mock LLM 测试？
- 哪些动作是危险动作，为什么危险？
- 反馈信号如何客观、确定、可回灌？
- CLI/TUI 和最小 WebUI 各自承担什么职责？

本阶段产生的关键对话和决策，之后要写入 `SPEC_PROCESS.md`。

---

## 3. 编写 `SPEC.md`

`SPEC.md` 是第一个核心交付物。它必须来自 brainstorming 的结果，而不是直接边写边猜。

通用要求必须包含：

- 问题陈述：解决什么问题、目标用户是谁、为什么值得做。
- 用户故事：至少 5 个，并符合 INVEST 原则。
- 功能规约：按模块写清输入、行为、输出、边界条件、错误处理。
- 非功能性需求：性能、安全、可用性、可观测性。
- 系统架构：组件图、数据流、外部依赖。
- 数据模型：主要实体、字段、关系、约束。
- 凭据与分发设计：key 如何录入、存储、更新、清除；如何分发。
- 技术选型与理由：Python、测试框架、CLI/TUI、WebUI、LLM 供应商等。
- 验收标准：每个功能的完成判定。
- 风险与未决问题。

### `SPEC.md` 中 A 项目额外必须写的内容

必须增加一节：

> 领域与机制设计

这一节至少回答：

| 机制类别 | SPEC 中要写清楚的问题 |
| --- | --- |
| 动作 / 工具 | agent 能读文件、写文件、运行测试、执行哪些受限 shell 命令？ |
| 客观反馈信号 | 测试结果、lint/type check、文件校验器如何转换为反馈并回灌？ |
| 危险动作 | 删除文件、越界写入、网络发布、危险 shell 命令如何识别和拦截？ |
| 记忆 | 项目约定、历史决策、失败修正记录如何存储和检索？ |
| 重点维度 | 为什么选择治理护栏 + 反馈闭环作为主要贡献？ |
| 可测试性 | 移除真实 LLM 后，哪些机制仍能用 mock LLM 单测验证？ |

---

## 4. 编写 `PLAN.md`

在 `SPEC.md` 签字确认后，触发 Superpowers 的 `writing-plans` 技能，把设计拆成小任务。

每个 task 必须包含：

- 目标。
- 涉及文件路径。
- 预期实现要点。
- 验证步骤。
- 将要先写的失败测试。
- 依赖关系。
- 是否可以并行。

任务粒度应控制在一个 subagent 一次会话能完成。通用要求建议每步约 2 到 5 分钟，但实际可以按“小而可验证”的原则拆分。

推荐任务顺序：

1. 项目骨架与测试命令。
2. 核心数据模型：Action、Observation、ToolResult、FeedbackSignal、GuardrailDecision。
3. mock LLM 抽象层。
4. agent 主循环。
5. 工具注册与分发。
6. 文件读写工具。
7. 受限 shell / test runner 工具。
8. 治理护栏。
9. HITL 审批状态。
10. 反馈传感器与失败分类。
11. 记忆存储与检索。
12. CLI/TUI。
13. 最小 WebUI。
14. 凭据存储。
15. Docker 分发。
16. CI。
17. README、机制演示、反思报告。

---

## 5. 编写 `SPEC_PROCESS.md` 的第一部分

在正式实现前，先把规约生成过程记录下来，后续冷启动验证后再补全。

需要记录：

- brainstorming 的关键节点。
- AI 追问了哪些好问题。
- 哪些问题让你修正了原设想。
- 至少 3 轮关键迭代的对话节选。
- 哪些建议被采纳，哪些被推翻，为什么。
- 对 brainstorming 技能的初步评价。

注意：这不是最后才补的流水账，而是过程证据。

---

## 6. 用陌生智能体做冷启动验证

正式实现前，必须找一个和主开发智能体不同的 agent，启动全新 session，不导入历史上下文或 memory，只给它 `SPEC.md` 和 `PLAN.md`。

要求它从 `PLAN.md` 中选 1 到 2 个 task 自主推进，并明确：

> 遇到不确定之处即暂停询问，不要凭猜测继续。

你要观察并记录：

- 它在哪里暂停提问？
- 哪些 spec 假设没有写清？
- 它有没有做出与你原意不一致的解读？
- 是 spec 写错了，还是它读错了？
- 产出和预期差距多大？

然后根据验证结果修订 `SPEC.md` 和 `PLAN.md`。

### 冷启动验证要写入 `SPEC_PROCESS.md`

记录内容包括：

| 记录项 | 需要写什么 |
| --- | --- |
| 暂停点 | 第二个 agent 因为什么不确定而暂停 |
| 暴露的缺陷 | SPEC / PLAN 哪些地方不够明确 |
| 偏差判断 | 是文档问题还是 agent 误读 |
| 修订动作 | 修订前后关键 diff |
| 结论 | 冷启动验证证明了什么 |

---

## 7. 初始化仓库和项目骨架

只有在 `SPEC.md`、`PLAN.md` 完成并经过冷启动验证后，才开始写实现代码。

需要建立 Python 项目骨架：

- `src/`：harness 源码。
- `tests/`：单元测试与机制演示测试。
- `examples/`：mock LLM 演示场景。
- `docs/`：可选补充文档。
- `pyproject.toml`：依赖、测试、格式化配置。
- `Makefile`：一键命令。
- `README.md`：后续持续更新。
- `AGENT_LOG.md`：从此时开始记录实现过程。

最低命令建议：

```bash
make test
make lint
make demo
make run
```

---

## 8. 按 worktree / PR / subagent 执行实现任务

实现阶段不能一次性在主分支上堆完代码。要求每个独立功能或大模块开一个 git worktree，对应一个 PR。

每个 task 的标准流程：

1. 开 worktree。
2. 派新鲜 subagent。
3. 先写失败测试。
4. 运行测试，确认红色。
5. 写最少实现让测试通过。
6. 运行测试，确认绿色。
7. 重构。
8. 请求两阶段 review。
9. 修复 critical issue。
10. 合并或保留分支。
11. 更新 `PLAN.md`，标记完成并附 commit hash。
12. 更新 `AGENT_LOG.md`。

---

## 9. 严格执行 TDD

TDD 是硬性要求，不接受先实现再补测试。

对 A 项目尤其重要的是：核心机制必须能在 mock/stub LLM 下确定性测试。

必须覆盖的机制测试：

- agent 主循环能按 LLM 输出解析动作、执行工具、回灌 observation。
- 工具分发能找到正确工具并处理错误。
- 治理护栏能拦截危险动作。
- HITL 状态能暂停并等待审批。
- 测试失败能被反馈传感器分类并回灌给 agent。
- mock LLM 能根据反馈改变下一步动作。
- 记忆能写入、检索，并按需注入上下文。
- 停机条件能正确结束循环。

---

## 10. 实现 harness 内核

A 项目的核心是自己编码 harness 内核。不能用 LangChain AgentExecutor、AutoGen、CrewAI、LlamaIndex agent runner 或宿主编码智能体的 agent loop 来代替。

建议模块拆分：

- `llm`：LLMClient 抽象、MockLLMClient、真实供应商 client。
- `loop`：agent 主循环与停机判断。
- `actions`：动作 schema、解析、校验。
- `tools`：文件工具、shell/test 工具、工具注册表。
- `guardrails`：危险动作识别、策略匹配、HITL 状态。
- `feedback`：测试结果解析、失败分类、反馈信号。
- `memory`：项目约定、历史决策、运行记录。
- `config`：声明式策略与项目配置。
- `cli`：命令行入口。
- `tui`：终端式交互界面。
- `web`：最小 WebUI。

---

## 11. 完成机制演示

A 项目额外要求必须提交机制演示。它可以是测试用例，也可以是可重复运行脚本。

必须确定性复现三件事：

1. 治理护栏拦截一个危险动作。
2. 注入一次失败，反馈闭环让 agent 收到反馈并改变下一步动作。
3. 重点维度的一个确定性行为。

如果重点维度是“治理护栏 + 反馈闭环”，第三项可以设计为：

> 同一个危险 shell action 在 mock LLM 输出中出现时，策略引擎先拦截并进入 HITL；审批拒绝后，agent 收到结构化反馈，下一步改为安全的 test runner action。

---

## 12. 实现凭据安全

凡调用真实 LLM 或其他鉴权 API，必须处理 API key。

需要实现：

- 首次运行引导用户安全录入 key。
- 隐藏输入。
- 存储到 OS keyring 或安全替代方案。
- 查看 key 状态时不回显明文。
- 支持更新 key。
- 支持清除 key。
- `.env` 只能作为 fallback，并说明明文风险。

`SPEC.md` 和 `README.md` 都必须说明威胁模型与对策。

---

## 13. 实现 CLI/TUI 与最小 WebUI

项目主要交互可以是终端式，不必做复杂网页。Open Design 对纯 CLI / 纯后端项目可豁免。

但最终交付清单要求提供可访问 WebUI，因此建议做最小 WebUI：

- 显示 run trace。
- 显示 action / observation。
- 显示 guardrail decision。
- 显示 feedback signal。
- 提供 mock demo 触发按钮或展示固定演示结果。

在 `SPEC.md` 中说明：

> 本项目主要界面是 CLI/TUI，因此不采用 Open Design；为满足最终交付清单，额外提供只读/演示型 WebUI。

---

## 14. 完成分发

至少选择一种分发形态。推荐 Docker。

Docker 分发需要做到：

- 单条 `docker build` 可构建。
- 单条 `docker run` 可启动。
- README 写清运行命令。
- README 写清 key 如何在目标机器安全配置。
- 写清已知限制。
- CI 中包含镜像构建步骤。

Python 包分发可作为加分项，但不是必须。

---

## 15. 配置 CI/CD

最终清单要求 `.gitlab-ci.yml`，且必须包含一个名为 `unit-test` 的 job。

需要包含：

- 安装依赖。
- 运行 `pytest` 或 `make test`。
- 若使用 Docker 分发，构建镜像。
- 最后一次 CI/CD 必须是 pass。

注意：通用要求正文里提到 GitHub Actions，但最终清单明确写 `.gitlab-ci.yml`。保守做法是优先满足 `.gitlab-ci.yml`，必要时再补 GitHub Actions。

---

## 16. 完成 README

README 必须包含：

- 项目简介。
- 安装方式。
- 运行方式。
- 分发命令。
- 目录结构。
- 安全边界说明。
- key 安全配置方式。
- 已知限制。
- 机制演示运行方式。
- WebUI 访问方式。

README 还应明确：

- harness 内核是自己实现的。
- 没有使用现成 agent 编排框架作为主循环。
- mock LLM 测试不依赖网络和真实 LLM。

---

## 17. 持续维护 `AGENT_LOG.md`

实现过程中每个关键节点都要记。

每条日志建议包含：

- 时间戳。
- task 编号。
- 触发的 Superpowers 技能。
- 关键 prompt / context 配置。
- subagent 输出关键片段。
- commit hash。
- 人工干预：改了什么、为什么。
- 学到的教训。

这是过程证据，不是最后补一篇总结。

---

## 18. 完成 `REFLECTION.md`

反思报告要求 1500 到 2500 字，并且必须由学生本人撰写。可以用 AI 辅助润色，但需要标注。

建议覆盖：

- 哪些 Superpowers 技能最有用。
- 哪些流程形式大于实质。
- TDD 在 AI 协作下是阻碍还是放大器。
- subagent-driven 工作流能自主运行多久。
- 什么 task 粒度最合适。
- SPEC / PLAN 质量如何影响实现。
- 一个规约不清导致 subagent 偏离的具体案例。
- 最有效的 prompt / context 策略。
- 凭据与分发要求迫使你想清了什么。
- 如果重做会改变什么。
- 对 Superpowers 方法论的批判。

---

## 19. 最终自查

提交前逐项检查：

- `SPEC.md` 已完成，并包含 A 项目的“领域与机制设计”。
- `PLAN.md` 已完成，task 有验证步骤和失败测试说明。
- `SPEC_PROCESS.md` 已记录 brainstorming 与冷启动验证。
- 源代码包含自己实现的 harness 内核。
- mock/stub LLM 单元测试可离线运行。
- 机制演示可重复运行。
- TDD 过程有证据。
- `AGENT_LOG.md` 持续记录过程。
- README 包含要求章节。
- 凭据没有硬编码、没有提交、没有日志泄露。
- Docker 或其他分发方式可运行。
- `.gitlab-ci.yml` 包含 `unit-test` job。
- 最后一次 CI/CD 是 pass。
- 有线上部署 URL 和可访问 WebUI。
- `REFLECTION.md` 完成。
- 仓库有完整 commit 历史和 PR / worktree 过程证据。

10. 按 worktree + subagent + TDD 实现。
11. 完成 mock LLM 机制测试。
12. 完成 CLI/TUI。
13. 完成最小 WebUI。
14. 完成凭据安全。
15. 完成 Docker / 分发。
16. 配置 CI/CD。
