# YB-agent V2.0 总体设计与执行契约

版本 1.0 · 2026-10-20 · 状态：经二次独立审查定稿；第一阶段实施进度见 IMPLEMENTATION_LOG.md。

## 1. 目标、事实基线与适用范围

目标是通过自主设计执行内核深入学习 Agent，并形成可使用、可验证、可解释设计取舍的项目。Agent 智能能力与工程可靠性均需要验证，不能用框架复杂度替代任务效果。

当前代码已经具有循环、工具、护栏、反馈、记忆和 mock 演示。源码可见的主要边界：

| 代码 | 可见行为 | V2.0 处理方向 |
| --- | --- | --- |
| `src/loop.py` | 循环集中处理调用、审批、执行和记录，运行轨迹在内存构造 | 明确决策、状态推进与外部执行边界 |
| `src/models.py` | Step 绑定单个 Action；缺少独立的调用尝试和验收模型 | 重新定义领域语义 |
| `src/guardrails/chain.py` | 遇到需要审批即返回，后续规则可能未评估 | 硬拒绝优先，汇总必要审批 |
| `src/tools/shell.py` | 同步 `subprocess.run`、`shell=True`、工作目录与超时 | 受控参数调用、基本进程监管和真实能力边界 |
| `src/context.py` | 结果回灌截取前 500 字符，采用自定义 JSON 动作协议 | 结构化观测、输出制品和协议完整性 |

上述为源码阅读结论，不等于已复现运行缺陷或已完成安全审计。旧版的确定性测试思想和示例可评估复用，但测试断言需与 V2.0 契约重新对应。

## 2. 架构与依赖方向

```text
CLI / 后续 WebUI
    -> 应用服务：提交、控制、查询、人工处理
        -> Agent Engine：推进 Run / Step
            -> Context / Decision Policy / Model Adapter
            -> Policy / Approval / Budget
            -> Tool Executor / Feedback / Verification
        -> 记录与存储适配器
第二阶段新增：持久化调度、Recovery、长期记忆与检索、委派协调
```

引擎依赖小范围的协议和领域数据，不直接依赖 CLI、Web、具体模型 SDK 或 SQL。不得为全部未来扩展提前创建空服务和宽泛仓储接口；只有被当前切片使用的边界才实现。

第一阶段核心可以组织为领域模型、引擎、模型、上下文、工具、策略、记录和 CLI。确切包结构在 P1-01 核对后记录，避免与旧 `src` 包及入口发生隐式覆盖。新旧入口切换必须有兼容策略，不能在本方案落盘时宣称已经迁移。

## 3. 领域语义

| 对象 | 责任与关系 |
| --- | --- |
| Task | 用户目标、约束和验收条件，可有多次 Run |
| Run | 一次执行；重做创建新 ID，第二阶段恢复保留原 ID |
| Step | 一轮模型决策及其观测收集；每 Run 按序编号 |
| ModelAttempt | 一次模型请求；记录输入引用、配置、结果、使用量与不确定性 |
| Decision | 一个 Step 最多接受一个不可变决策：工具调用集合或最终回答 |
| ToolCall | 一次逻辑动作，属于已接受 Decision；固定工具版本、参数和顺序 |
| ToolAttempt | ToolCall 的一次实际尝试；重试新增尝试，不覆盖历史 |
| Approval | 对确定动作版本的授权；保存主体、范围、条件和有效性 |
| Artifact | 完整输出、补丁、文件快照等，带格式版本和校验信息 |
| Evidence / Assessment | 结论依据、验收条件、检查范围与判定 |
| Event | 运行中已确认的状态变化；第二阶段与正式状态同事务提交 |

阶段二按需要实现 PlanRevision、MemoryEntry、Delegation 等对象，不预先要求各自独占一张表。

### 3.1 Decision 与 Step

无效响应保留 ModelAttempt 错误，不产生可执行 Decision。重试受协议错误预算限制。Step 接受 Decision 后不得替换；需要新行动时创建新 Step。

一阶段可接受模型一次提出多个 ToolCall，但按返回顺序串行处理，每个调用单独治理。先成功的调用不因后续失败自动回滚。明确失败、拒绝、跳过均形成可观察结果；本轮调用全部得到观测后 Step 进入 SETTLED，再创建下一 Step。

示例：三次调用两次成功、一次明确失败，Step 可 SETTLED，Run 不必 FAILED；下一轮根据全部反馈决定行动。取消或预算耗尽使 Run 结束时，尚未授权启动的调用终结为未执行并记录原因，不能伪造工具响应成功。暂停仅保留这些调用为待执行，不将其标记为永久跳过；同进程继续后重新检查启动条件，仍属于原 Decision 和 Step。

一阶段遇到副作用结果 UNKNOWN，终止 Run 为 FAILED，原因 `TOOL_OUTCOME_UNKNOWN`，保留未决事项，不自动核对或续跑。二阶段改为 WAITING / RECONCILIATION，按恢复规则处理。暂停可以停在调用之间，保留尚未执行的调用；原生模型协议在本轮全部闭合前不得发起下一模型决策。

### 3.2 ID 与版本

每个 Run、Step、Decision、ToolCall、Attempt 独立标识。相同参数不构成全局去重依据。恢复重试保留逻辑调用 ID，新增 Attempt；外部幂等键按工具协议使用。

参数改动或目标变化创建新动作，原审批不自动迁移。上下文、工具协议、政策和制品均记录版本；版本不兼容时停止并说明，不猜测迁移。

## 4. Run 状态与控制契约

第一阶段状态：QUEUED、RUNNING、WAITING、PAUSED、COMPLETED、FAILED、CANCELLED、EXHAUSTED。第二阶段增加 RECOVERING。等待原因独立记录；控制请求为 NONE、PAUSE、CANCEL。第一阶段无跨进程调度，QUEUED 仅表示等待本地执行者。

| 当前状态 | 条件 | 允许处理 |
| --- | --- | --- |
| QUEUED | 认领成功、无阻止启动的控制请求 | RUNNING |
| QUEUED | 取消先被接受，尚无启动许可 | CANCELLED |
| QUEUED | 暂停先被接受，尚无启动许可 | PAUSED，保留待执行内容 |
| RUNNING | 审批、工具结果、重试时间或资源未满足 | WAITING，并给出原因 |
| WAITING | 等待条件满足且控制允许 | QUEUED，重新检查后推进 |
| RUNNING / WAITING | 收到 PAUSE | 先记录请求、停止新许可；安全边界后 PAUSED |
| PAUSED | 同进程内继续且重新检查通过 | QUEUED |
| RUNNING / WAITING / PAUSED | 收到 CANCEL | 停止新许可，处理已有执行，确认后 CANCELLED |
| 非终态 | 二阶段取得接管资格 | RECOVERING，核对后排队、等待、暂停或终止 |
| RUNNING | 最终决策、输出和记录提交成功，控制请求允许，无未决执行 | COMPLETED |
| 执行中 | 预算耗尽 / 不可继续错误 | 停止新许可，处理已有执行后 EXHAUSTED / FAILED |
| 任一终态 | 重复命令、迟到结果 | 不重新调度；返回已有状态或附加核对证据 |

暂停保证不再启动新动作，受监管执行已到达约定边界；不承诺冻结任意远程动作。取消确认前保持原状态并展示请求进度；取消不等于回滚。无法终止的外部动作必须登记未决事项，不得显示“所有动作已停止”。

第一阶段暂停默认等待当前工具返回或达到其执行上限，再保留后续调用进入 PAUSED，不把杀死进程解释为可继续执行。需要中止当前工具时使用取消流程。等待审批期间收到暂停或取消时，控制入口仍须响应，审批通过本身不能越过已接受的控制请求。

控制与最终提交在同一串行控制边界内排序。取消/暂停先被接受时阻止 COMPLETED 提交；若终态先提交，后来的控制返回该终态。第一阶段使用单执行者控制入口；二阶段使用事务、版本和执行代次。

已接受 CANCEL 后，到终态提交前禁止接受新的 PAUSE/RESUME 来清除取消请求；重复 CANCEL 幂等。错误或预算耗尽与取消竞争时，以同一控制入口的接受顺序确定处置：取消已接受则完成取消处置并提交 CANCELLED，同时保留错误、耗尽和未决事项；其他终态已提交则返回该终态。PAUSE 不覆盖必须停止执行的错误，错误及未知副作用按其规则处理。

控制默认针对 run_id。Task 级批量控制、第二阶段父子任务传播均是独立显式操作。第一阶段进程退出后 PAUSED Run 不支持重新加载续跑。

### 4.1 不变量

- I-01：终态不得再次调度；重做创建新 Run。
- I-02：每 Step 最多接受一个 Decision；每次实际尝试都有独立记录。
- I-03：硬性拒绝不可被审批覆盖；未满足所需审批的动作没有启动许可。
- I-04：动作参数和审批条件一致；变化后重新评估。
- I-05：取消先于许可提交时不得产生新许可；许可在先时仅承诺尽力取消并核对结果。
- I-06：UNKNOWN 不按普通失败自动重试；Run 终态不掩盖未决副作用。
- I-07：COMPLETED 不隐含验收 PASSED；证据范围和新鲜度可追溯。
- I-08：模型、工具、反馈或子 Agent 不能自行扩大权限与预算。
- I-09：二阶段状态推进必须验证有效执行资格；失联不等于外部动作停止。
- I-10：每次模型请求发送或重发都受 Run 控制边界排序；意图记录、预算预留不等于发送许可。控制在先不得开始新请求，迟到响应不得使已取消 Run 重新推进。

## 5. 工具启动、策略与执行

启动许可是系统接受一次尝试的逻辑边界，不是外部副作用发生的物理时刻。许可前检查状态、控制、动作版本、所有策略、审批、资源和预算；串行提交许可与 Attempt 后执行。

取消与许可通过同一 Run 控制边界排序。许可之后仍应尽力检查撤销并停止尚未真正启动的操作，但不能用最后一次检查承诺消除所有外部竞争。二阶段许可必须持久化，执行入口核对许可并防止重复接受；外部效果仍依赖工具能力。

策略聚合先检查硬拒绝，再汇总审批要求，最后允许。批准只满足对应要求，不能跳过未检查规则。审批保存不可变动作版本/规范化摘要、主体、资源、策略版本、有效期和关键前置条件；摘要不是授权凭据。拒绝后允许模型选择合规新动作，不能绕过拒绝范围。

基础工具包含读取、受控写入和命令执行。命令优先 program + args，原始 Shell 默认关闭；测试同样属于代码执行。命令、子进程和文件工具不阻塞控制事件循环；线程取消不等于底层执行停止。

第一阶段最低安全边界：用户选定的可信/受控项目、副本工作区、路径与链接检查、写前版本校验、敏感文件排除、子进程最小环境、输出限制、超时和基本进程树监管。工作目录和正则不是操作系统沙箱；不宣称可以安全执行任意恶意仓库。遇到无法可靠约束的执行请求，拒绝或要求改用已验证的隔离方式。

Windows/Linux 分别验证进程监管、链接和路径行为。写前哈希只用于发现修改，不能单独消除检查到写入间竞争；结合受控单写者工作区和适当文件操作，冲突无法排除时停止覆盖。

工具输出区分成功、明确失败、UNKNOWN、拒绝与未执行。错误分类至少覆盖输入/协议、权限、审批、超时、环境、模型传输、工具业务失败、记录存储失败和不确定副作用。只读查询可有限重试但结果可能变化；写操作未声明安全重试能力时不自动重试。

## 6. 模型、上下文、预算与本地记录

Model Adapter 规范化文本、原生工具调用或兼容 JSON 决策、结束原因、使用量和请求标识。未配置真实模型时明确失败，不能静默切换 mock。运行器与 SDK 重试预算统一，模型响应不保证可重复生成。

第一阶段在发出模型请求前建立 ModelAttempt 意图，记录输入/配置引用；这只提供审计，不提供跨崩溃可靠性。第二阶段要求先持久化意图再请求。发送后响应或用量未知时显式记录，不按零成本计算。

模型请求同样属于受控启动动作，但不伪装成外部工具调用，也不自动要求工具审批。建立 ModelAttempt 和预留额度后，必须通过与暂停、取消相同的串行控制入口，重新检查 Run/Step、控制请求、执行资格、输入与模型配置引用和剩余额度，接受本次请求的发送许可。第一阶段采用单执行者控制边界，第二阶段将许可、尝试和对应事件持久化。这个许可是系统接受启动的逻辑提交点，不是供应商收到请求的物理时刻。

| 控制与模型请求的先后 | 必需行为 |
| --- | --- |
| PAUSE / CANCEL 先于发送许可被接受 | 不发送本次请求，记录未发送原因；确认没有发出时释放相应额度预留 |
| 发送许可在先，随后 PAUSE / CANCEL | 尽力撤销尚未发送的请求或取消在途请求；不承诺供应商停止处理或不计费，不重发以试图取得确定结果 |
| 已接受 PAUSE，完整响应随后到达 | 保存响应、使用量和输入引用，停止接受新决策及工具启动；到达可保存边界后 PAUSED。继续时核对适用性，复用有效响应；失效时记录原因，再按新许可决定是否新增尝试 |
| 已接受 CANCEL 或 Run 已取消，响应随后到达 | 仅保存允许接收的观测与使用量，不接受新的 Decision、不发工具调用、不恢复任务、不覆盖终态 |

模型等待必须有截止时间；暂停不承诺冻结供应商端执行，超时和用量未知均显式记录。每次重发与外层重试都重新检查控制和预算并保留尝试，不复用已经失效的许可；无法接入该约束的 SDK 自动重试须关闭。接收响应、接受 Decision 与最终提交也通过控制边界排序。P1-04 落实基本发送资格，P1-07 完善交互控制和确定性竞争验证。

上下文保留用户目标、约束、最近观测和完整调用关联。工具调用与对应响应成组保存，未闭合前不发起下一模型决策；大输出写制品并提供摘要、截断标记和按需读取。超出预算且无安全裁剪方式时明确停止。高级语义压缩留到第二阶段。

外部文件、网页、工具输出、检索记忆作为带来源的数据，不能提升为系统授权。输入材料发给外部模型的范围遵循用户任务授权，凭据与敏感内容排除/脱敏。

预算覆盖步骤、模型请求/Token、工具尝试、执行时长和重试。发送前检查/预留，结束后结算；实际成本未知时保守记录。等待用户审批的时间与执行预算、整任务截止时间分开配置，禁止所有等待无区别扣减。

第一阶段本地目录按 Run 隔离，保存 manifest、事件 JSONL、最终报告及制品；包含 schema_version、序号和校验信息。输出在暂存文件完成后替换最终文件，读取时识别不完整记录。归档失败必须报告，不能宣称完整可追溯。凭据使用引用，不写入审计内容。

第一阶段不承诺强杀前最后事件已落盘、不自动重放、不自动清除残留进程；启动后只将可识别的未结束记录报告为异常中断并提供人工检查说明。结果不确定仍须如实报告。

## 7. 验收证据与评测

Assessment 取 PASSED、FAILED、PARTIAL、UNVERIFIED、INCONCLUSIVE，与 Run 终态独立。每项验收条件关联模型声明、工具观测或按明确判据执行的验证。模型声明单独不足以判通过。

代码修改后的检查绑定工作区版本/内容标识、命令、退出码、输出和范围；之后相关内容变化使对应证据失效。测试通过只支持所覆盖条件。必须条件全部有有效通过证据才能 PASSED；任一必须条件明确失败则 FAILED；证据缺失和无法判断分别说明，不能用多数投票掩盖失败。

机制测试和真实模型评测分开。前者检验确定性规则；后者保存任务清单、环境、模型配置、各次结果、使用量和证据。固定样本及预算后进行配置对照，不删除失败或预算耗尽的尝试。

阶段一能力门槛按基线制定，不预设未经验证的固定通过率。P1-03 先版本化任务、必需验收条件、预算、重复次数和开发/最终评测样本的使用规则；P1-04 建立只读任务基线，P1-06 在安全工具就绪后补齐修复和多步检查基线。每类基线形成后冻结该类的发布阈值及理由，全部目标在 P1-06 结束前写入同一评测规范。阈值是后续最终评测的硬门槛，不得在看到最终结果后放宽。任务、预算或阈值变化须版本化并重新评测，旧失败保留；用于调优的尝试不得混入最终发布结果。缺少冻结的数值、预算、重复次数或样本规则时，P1-12 与 G1 均不能通过。

安全、控制、证据正确性的必需确定性场景必须全部通过，不用平均成功率替代。真实能力验收至少要求三类任务各有可独立复核的成功案例，并满足提前冻结的分类阈值；所有失败、取消、耗尽和受阻尝试一并报告，不能只挑最佳一次。

阶段完成的阻断项是必需确定性检查失败、未达到分类发布阈值、未处置的安全/正确性缺陷，或缺少必需验证证据。达到分类阈值后仍存在的能力失败样本必须保留并分析，但不要求逐个消除以达到未经约定的 100% 成功率。

第二阶段 G2-R 与 G2 的正式交付配置必须重新满足适用的 G1 必需机制检查和已冻结分类能力门槛，记录任务、模型、预算、环境及配置版本；仅解释退化原因不能替代通过。对照实验中的策略或配置允许负收益，不要求所有实验变体达到发布门槛；它们不能被当作已通过的正式交付配置。确需修改原门槛或评测条件时，先按变更纪律形成新版本、说明影响，再开展新的最终评测，同时保留原基准的结果和差异；不得在看到最终结果后放宽门槛，或声称未通过原门槛的配置保持了 G1。

三类任务为受控仓库调查、含失败反馈的小型修复、带明确约束的多步检查，具体样本在实现前冻结。故障与取消的确定性用例独立于这三类能力任务。

## 8. 第二阶段恢复契约

正式存储采用当前状态 + 事务事件 + 制品引用，不要求全量 Event Sourcing。短事务边界：保存请求意图；接受决策并建立调用；提交启动许可与尝试；保存观测、状态和检查点。模型/工具执行期间不持有长事务。

数据库提交确认未知时按稳定 ID 查询再判断。制品先可靠保存校验再提交引用，处理孤立制品与引用损坏。重要执行记录使用满足恢复要求的持久性配置。

Worker 通过认领、租约、版本和执行代次取得资格。租约时间依据数据库时间；续租/接管通过条件更新验证。等待审批无需让 Worker 一直占用运行租约。工具执行有独立身份/句柄，其存在性不能由 Run 租约推断。

执行代次只能直接保护配合校验的写入。共享资源需要资源级控制；文件、远程请求和进程不因数据库拒绝旧写入自动停止。不支持 fencing 的工具依靠幂等、查询、单写者和核对；无法排除冲突时不启动新写入。

| 中断位置 | 恢复方式 |
| --- | --- |
| 模型请求意图已保存、响应未知 | 查询可用结果或新增尝试，保留用量未知记录 |
| 决策已保存、无有效启动尝试 | 检查配置/环境/审批/预算后调度 |
| 已有工具执行句柄 | 查询并监管旧执行，避免直接启动第二份 |
| 工具可能生效、无已保存结果 | WAITING / RECONCILIATION，按工具协议核对 |
| 工具结果已保存 | 使用既有结果继续，不默认重新读取变化后的外部数据 |
| 最终结果已提交、客户端未收到 | 返回既有结果，不创建重复 Run |

核对类型：只读重试、稳定幂等键、查询外部结果、人工处理或受治理补偿。补偿不是万能回滚。读取当前值等于期望值，也不能单独证明本次调用曾成功；需要说明核对依据及能证明的范围。

## 9. 第二阶段智能与应用扩展

- Planning：计划版本、依赖、产物、验证、重规划理由；完成状态由证据支持。反思由失败、停滞等事件触发并受预算限制。
- 上下文增强：分层摘要、来源引用、失效和协议完整性；恢复依据正式记录而非模型摘要。
- 长期记忆：来源、作用域、版本、适用条件、修订和删除；模型提炼先作为候选，不自动成为高权限规则。
- RAG：摄取/分块/索引/权限过滤/引用，处理更新与删除传播；索引可重建，不作为核心业务状态唯一副本。
- API/WebUI：Run 级控制、Task 级显式批量操作、幂等提交、事件游标、断线补读、审批与未决副作用处理。流式草稿与已提交最终结果区分。
- Multi-Agent：委派记录关联父子 Run，约定输入、权限、预算、验收与返回格式。共享预算预留结算；写工作区隔离并核对合并，外部资源另行治理。限制深度、数量和循环依赖。
- 子任务超时或取消不等于其外部动作停止；父任务不得仅因收到“完成”文字判定验收通过。全部扩展复用核心权限、记录和恢复约束。

## 10. 实施、兼容与验证纪律

第一阶段保留旧 v0.1.1 入口，先建立明确 V2 入口；切换与兼容在 P1-11 验收。内部对象允许重新设计，但已有用户入口和配置变更必须说明，不静默指向不同语义。

正式实施前检查 Git 状态和本机环境，运行旧版基线；已有失败先记录，不通过删测试或弱化断言消除。仅安装当前任务所需依赖，不为规划先启动数据库或服务。

每个任务先构造有区分力的失败/错误场景，再验证最小实现与必要回归；文档或纯低风险展示改动不强行增加镜像测试。阶段二数据库行为用正式 PostgreSQL 集成验证，不能用内存仓储替代锁与事务语义。

Windows PowerShell 命令基线：`python -m pytest tests/unit tests/demo -q`、`python -m ruff check src tests`；新增 V2 测试路径和入口命令在 P1-01 确定，写入阶段计划再使用，不假装当前已经存在。真实模型评测需单独显式运行，普通单测不消耗 API 额度。
