# 第二阶段计划：崩溃恢复与复杂扩展

版本 1.0 · 2026-10-20 · 状态：经二次独立审查定稿，实施未开始；依赖第一阶段 G1。

规范依据：[总体设计与执行契约](DESIGN.md)。基础交付见[第一阶段计划](PHASE1_PLAN.md)。

## 1. 目标与进入条件

在已经可用、可评测的单 Agent 上交付：B 崩溃恢复、持久化运行、执行接管、副作用核对、规划与上下文增强、长期记忆与 RAG、完整管理应用、Multi-Agent 和工程交付。

进入条件是 G1 真实完成，基础协议与测试可复用，任务集有固定基线。若基础循环、控制或证据尚不正确，先修复对应第一阶段问题，不用引入 PostgreSQL/Worker 掩盖。

第二阶段目标全部保留；按任务完成不等于提前宣布第二阶段整体完成。恢复子目标的独立门槛为 G2-R，全部扩展与交付门槛为 G2。

## 2. 技术与调度基线

- 正式运行存储使用 PostgreSQL，采用短事务、条件更新、版本化迁移；集成测试使用真实数据库。
- API 与 Worker 可分进程，核心仍为模块化单体；数据库可执行记录负责调度，不同时引入消息队列双写。
- 状态 + 同事务事件 + 制品引用，不要求完整 Event Sourcing；旧版本地审计不自动变成可恢复 Run。
- 部署脚本按用户授权创建和操作本项目资源，不自动停止现有数据库、Docker 或服务。
- Redis、消息队列、独立向量服务不是必需前置；确需引入先说明瓶颈或功能需求。向量实现选择在 P2-08 冻结。
- 所有新调用入口和子 Agent 复用已有权限、启动许可、预算与证据机制。

## 3. 任务依赖

```text
G1 -> P2-01 恢复故障模型
   -> P2-02 持久化与迁移 -> P2-03 执行协议与核对
   -> P2-04 调度接管 -> P2-05 故障注入与G2-R
   -> P2-06 规划反思 -> P2-07 上下文增强
   -> P2-08 记忆与RAG -> P2-09 完整API与WebUI
   -> P2-10 委派契约 -> P2-11 协作治理
   -> P2-12 对照评测与完整交付G2
```

恢复的最小人工处理入口随 P2-03 提供，诊断事件随 P2-02 提供，不等完整 WebUI 才能处理未知状态。每次增强保留 G1 与 G2-R 回归，不能靠“后续阶段再修”接受核心正确性退化。

| 里程碑 | 对应任务 | 可演示产出与通过条件 |
| --- | --- | --- |
| 2.1：恢复基础 | P2-01 至 P2-02 | 明确故障矩阵、正式运行存储和事务记录；可加载和校验已有执行事实 |
| 2.2：恢复正确性与 G2-R | P2-03 至 P2-05 | 人工核对入口、执行接管及真实进程中断演示；达到全部 G2-R 条件 |
| 2.3：Agent 能力增强 | P2-06 至 P2-08 | 规划、上下文、记忆与 RAG 的可用实现及对照报告，包含负收益和限制 |
| 2.4：完整应用 | P2-09 | Web 中完成任务控制、审批、轨迹查看和异常处理；断线后可核验已提交结果 |
| 2.5：协作与 G2 | P2-10 至 P2-12 | 受控委派、资源治理、单/多 Agent 对照与可复现交付；达到全部 G2 条件 |

阶段一的只读、修复和多步检查任务持续作为回归基线；新增复杂任务可单独扩充评测版本，不能通过删除原任务隐藏能力退化。

### P2-01：恢复场景、故障点与兼容契约

- [ ] 未开始。依赖：G1。
- 目标：在写表和加 Worker 之前确定恢复到底承诺什么。
- 范围：请求意图、Decision、许可、Attempt、结果、最终提交各边界；版本/环境/审批/预算检查；UNKNOWN 分类。
- 产出：故障矩阵、恢复决定表、来源/版本要求、外部工具恢复能力清单。
- 首要错误场景：模型已计费响应丢失；写成功结果丢失；提交成功确认丢失；文件已由用户修改。
- 验证：每种现场能唯一给出继续、查询、安全重试、等待人工或拒绝恢复的决定。
- 通过条件：不承诺任意工具恰好一次，不把租约过期当执行已停止，不把相同当前值当充分历史证据。

### P2-02：正式存储、事务事件与迁移

- [ ] 未开始。依赖：P2-01。
- 目标：让运行事实成为可恢复的正式数据。
- 范围：模型/工具意图与尝试、状态版本、事件序号、审批、制品引用、检查点；schema 迁移和配置持久性。
- 首要错误场景：事务提交未知、重复请求、制品保存后事务失败、引用缺失、旧 schema 不兼容。
- 产出：迁移脚本、仓储实现、稳定查询/幂等键、备份与恢复说明。
- 验证：真实 PostgreSQL 事务/约束测试，注入连接故障后按 ID 查询；验证状态与事件原子性，不在模型/工具执行期间持有事务。
- 通过条件：有效记录可重载；损坏显式失败；只读导入旧档案可以支持查询，但禁止据此自动续跑。

### P2-03：持久化启动许可、结果核对与最小恢复入口

- [ ] 未开始。依赖：P2-02。
- 目标：把执行授权和恢复判断落实到工具边界。
- 范围：许可/控制事务排序、执行入口去重、稳定操作标识、只读/幂等/查询/人工四类恢复、审批失效、迟到观测。
- 首要错误场景：取消先于许可；许可先于取消；许可后未启动就崩溃；外部成功而本地结果未知；迟到结果尝试覆盖终态。
- 产出：恢复协议、人工核对 CLI/API、受控工具的核对实现、未决事项与处置审计。
- 验证：同调用多 Attempt 保留历史；核对结论有证据；人工“重试/确认/放弃”有主体与权限，不允许删除证据伪造成功。
- 通过条件：无法安全判断时阻塞冲突动作；补偿是新受治理动作；不声称统一消除所有外部竞争。

### P2-04：Worker 调度、租约与资源接管

- [ ] 未开始。依赖：P2-03。
- 目标：多个执行者能取得明确资格并安全处理失联。
- 范围：认领、续租、数据库时间、执行代次、条件更新、退避和公平性；资源级单写者；工具句柄与执行者身份分离。
- 首要错误场景：旧 Worker 长暂停后恢复；续租失败；两个 Worker 竞争；接管时旧进程仍写文件；等待审批占用 Worker。
- 产出：调度器、接管处理、执行/资源资格检查、必要工具进程监管增强。
- 验证：真实双进程与可控屏障测试；旧状态写入被拒绝；不支持外部 fencing 时转向幂等/核对/阻塞，不仅增加一个 token 字段。
- 通过条件：I-09 成立；同一可写工作区不会因接管启动未经排除冲突的第二个写者；等待任务不空占执行线程和租约。

### P2-05：真实故障注入与 G2-R

- [ ] 未开始。依赖：P2-04。
- 目标：验证恢复保证与边界，而非仅在 mock 中抛异常。
- 范围：模型请求前后、许可前后、工具生效前后、结果提交前后和最终输出各故障点；重启、重复投递、外部变更与制品损坏。
- 产出：进程中断测试、逐故障证据、未支持工具的限制、恢复演示。
- 验证：实际结束任务创建的 Worker，重启后核对同一 Run；测试自己的进程/数据库，保留既有用户服务。
- 通过条件：G2-R 全部满足；安全不能靠平均通过率；数据库/凭据不可用导致未运行时明确受阻。

### P2-06：版本化规划、反思与动态调整

- [ ] 未开始。依赖：P2-05。
- 目标：在同一核心上比较直接执行与计划执行，增加复杂任务能力。
- 范围：PlanRevision、依赖、产物与验证；失败/停滞触发重规划；受限 Reflection；不建立脱离治理的新循环。
- 首要错误场景：反思无限增长、模型自报进度、已失效计划继续执行、恢复后计划与事实冲突。
- 产出：可替换策略、计划记录、实验配置与对照报告。
- 验证：相同任务和相近预算对照；保留无收益/负收益结果；恢复后遵循实际已完成调用。
- 通过条件：策略正确性、预算和恢复测试通过；结论有数据，不要求所有样本都比直接执行更好。

### P2-07：上下文压缩与恢复重建

- [ ] 未开始。依赖：P2-06。
- 目标：减少无效输入并保持任务约束与证据关联。
- 范围：分层摘要、引用和覆盖范围、失效、检索式读取、预算；从正式记录重建，摘要不是检查点。
- 首要错误场景：压缩掉用户限制、孤立调用、摘要误报完成、重启后上下文不同版本混用。
- 产出：策略、重建流程、长任务和协议回归数据。
- 验证：记录保留/遗漏信息与任务效果，比较 Token、成本、成功及错误；供应商估算误差说明。
- 通过条件：协议不变量和安全约束不退化；压缩失败可回退或明确停止。

### P2-08：长期记忆、知识摄取与 RAG

- [ ] 未开始。依赖：P2-07。
- 目标：让历史经验和知识有来源、可纠正、按权限检索。
- 范围：候选记忆、确认/失效/删除、作用域与版本；摄取/分块/关键词及向量检索/引用/增量更新。先选定基线再锁定必要依赖。
- 首要错误场景：跨项目泄露、旧文档召回、删除未传播、索引与 embedding 版本不一致、模型经验被当系统指令。
- 产出：记忆管理、索引流水线、源材料引用、权限测试和检索评测集。
- 验证：源更新/删除与权限变化的传播；索引可重建，核心执行状态不依赖向量唯一副本。
- 通过条件：能解释命中来源和限制；对照实验报告收益与局限，不能以“有向量库”代替有效性。

### P2-09：完整 API、WebUI 与人工处理闭环

- [ ] 未开始。依赖：P2-08；最小恢复入口此前已存在。若前序仅提供 CLI，本任务新增 HTTP API 并复用已有应用服务，不假定已有 API。
- 目标：用户不依赖内部实现知识即可操作、观察、审批与处理异常。
- 范围：Task/Run 查询、Run 控制、显式批量控制、幂等提交、事件游标与补读、制品、记忆/评测、审批和恢复页面。
- 首要错误场景：重复提交、同幂等键不同请求、断线、草稿被当正式结果、无权限审批、按钮取消而工具仍执行。
- 产出：接口契约、UI、身份与项目权限边界、交互文档。
- 验证：HTTP 连接结束不终止后台任务；已提交状态可重查；浏览器流式文本区分暂态；凭据不进入页面与 Trace。
- 通过条件：正常与异常流程端到端可复核；远程暴露要有认证授权，不自动视为生产平台。

### P2-10：委派协议与父子运行语义

- [ ] 未开始。依赖：P2-09。
- 目标：先明确协作契约，再添加角色或并发执行。
- 范围：Delegation、输入/产物/验收、父子 Run、预算预留、权限子集、超时、取消、重启关联、深度与依赖环。
- 首要错误场景：重复委派、子任务假报完成、父取消但子仍写、重启后找不到既有子 Run、预算重复计算。
- 产出：协议、状态转换、聚合规则和确定性协作样例。
- 验证：父运行以已保存委派恢复关联；子结果含证据，聚合不能以多数投票覆盖必需检查失败。
- 通过条件：父子状态与外部事实分开；终态、预算与权限不变量全部适用。

### P2-11：协作执行、资源冲突与结果汇总

- [ ] 未开始。依赖：P2-10。
- 目标：在明确作用域中运行专业子 Agent 并保持单 Agent 保证。
- 范围：受限并发、工作区/补丁、外部共享资源、协调与合并、取消传播、部分失败和核对。
- 首要错误场景：两子任务改同文件、Reviewer 无证据通过、共享外部资源冲突、一个子任务失联、取消过程中返回迟到结果。
- 产出：真实委派样例、合并/冲突说明、资源与预算记录。
- 验证：独立工作区不被当成所有副作用隔离；父运行统一验收而非盲信子 Agent。
- 通过条件：相同核心治理与恢复回归通过；角色名称不作为能力或正确性证据。

### P2-12：对照评测、可复现部署与 G2

- [ ] 未开始。依赖：P2-11。
- 目标：形成可学习、可使用、可展示的完整成果。
- 范围：单/多 Agent、规划/直接执行、压缩/记忆/RAG 的对照；故障演示、安装、迁移、备份、恢复、资源清理、限制与设计决策。
- 产出：全部实验结果、部署说明、架构/协议文档、演示任务和阶段报告；发布材料可准备，外部发布需另有授权。
- 验证：相近总预算、固定任务版本、重复尝试完整记录；新环境从文档复现；迁移/备份实际恢复后检查一致性。
- 通过条件：G2 所有目标有证据；负收益实验如实解释，不能只展示最佳结果。

## 4. G2-R 与 G2

### G2-R：崩溃恢复完成

- [ ] P2-01 至 P2-05 完成；正式交付配置按 DESIGN §7 重新通过适用的 G1 必需机制检查和冻结的分类能力门槛。退化归因不能替代通过，缺少验证或低于门槛均阻断 G2-R。
- [ ] 模型意图、决策、许可、工具执行、结果提交、最终交付的故障点真实验证。
- [ ] 进程退出后恢复同一 Run；既有结果不默认重放；不确定副作用进入合规核对。
- [ ] 双执行者竞争与旧执行者恢复场景通过，资源侧限制如实说明。
- [ ] 版本、审批、权限、环境和预算变化可阻止不安全续跑。
- [ ] 有可用人工处理入口与处置审计；取消和补偿不被描述为无副作用回滚。

### G2：完整扩展完成

- [ ] G2-R 保持通过，P2-06 至 P2-12 全部有产出与证据；完整版本的正式交付配置再次满足 DESIGN §7 的 G1 门槛。负收益实验可保留，不作为正式交付配置的通过依据。
- [ ] Planning、上下文增强、记忆/RAG 和 Multi-Agent 均有正确性检查与对照结果。
- [ ] 完整应用具备可用审批、恢复、轨迹与控制闭环；Task/Run 语义明确。
- [ ] 模型/工具使用量、成功/失败/未完成、人工介入和限制完整报告。
- [ ] 新环境可重建运行环境、迁移与恢复数据，文档与实际命令一致。
- [ ] 生产高可用或多租户未另行验收时，不在项目描述中声称具备。
